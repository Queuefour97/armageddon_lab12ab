### ⚙️ Detailed Breakdown: How the Python Code Works

The execution flow in `lambda_handler` is a masterclass in data pipeline orchestration. Here is the step-by-step journey of a report:

#### Step 1: Time Window Calculation
The Lambda calculates two distinct time windows:
*   **Current Period**: The last `REPORT_PERIOD_HOURS` (e.g., now back to 24 hours ago).
*   **Previous Period**: The 24 hours *before* the current period. 
*   *Why?* This allows the code to calculate `period_changes` (e.g., "WAF blocks increased by 15% compared to last week"), which is critical for executive trend analysis.

#### Step 2: Data Retrieval & Python-Side Filtering
The `retrieve_reporting_data` function scans all three DynamoDB tables (`waf-events`, `correlation-findings`, `security-incidents`). 
*   It uses a custom `scan_table` helper that implements **pagination**. It checks for `LastEvaluatedKey` and loops until it has gathered the data or hit the `MAX_ITEMS_PER_TABLE` limit.
*   It then uses `filter_records_by_period` to discard any records that fall outside the specific 24-hour windows. *(Note: Scanning and filtering in Python is a known anti-pattern for massive datasets, but your `MAX_ITEMS_PER_TABLE` cap makes it perfectly safe and acceptable for this lab).*

#### Step 3: Deterministic Metric Calculation
The code uses Python’s `collections.Counter` to rapidly aggregate the data:
*   **WAF Metrics**: Counts blocks vs. allows, identifies top source IPs, top targeted URIs, and top triggered rules.
*   **Finding Metrics**: Calculates average risk scores, counts by severity, and identifies the single highest-risk source IP.
*   **Incident Metrics**: Tracks open vs. resolved incidents, playbooks invoked, and calculates the age of the oldest open incident.

#### Step 4: AI Executive Narrative (Bedrock)
The aggregated metrics are packaged into a compact `evidence` dictionary and sent to Bedrock. 
*   The prompt strictly forbids the AI from inventing facts, claiming successful exploitation, or recommending automatic containment. 
*   If Bedrock succeeds, it returns a structured JSON narrative. If it fails, `create_fallback_naive` generates a safe, deterministic summary using string interpolation.

#### Step 5: Synchronized Document Assembly
The `build_report_document` function merges the deterministic metrics and the AI narrative into a single, unified Python dictionary. This guarantees that the PDF and the JSON file will contain the **exact same data**, ensuring data parity.

#### Step 6: In-Memory PDF Generation (`generate_pdf`)
Using the `reportlab` library, the code builds a "story" (a list of PDF elements):
1. Adds a centered Title and Subtitle.
2. Adds the Overall Security Posture in bold red text.
3. Adds the Executive Summary and a formatted Metrics Table.
4. Adds bulleted lists for Material Changes and Leadership Attention.
5. Inserts a `PageBreak()`.
6. Adds detailed SOC tables (Top URIs, Top Rules, Top IPs).
7. Writes the entire "story" to an `io.BytesIO()` memory buffer and returns the raw bytes.

 final step uploads both the `pdf_bytes` and the `json_bytes` to S3 using `put_object`. It applies `ServerSideEncryption="AES256"` and attaches custom metadata (like `report-id` and `security-posture`) to the S3 objects for easy searching later.

### 🔧 Recommended Refinements & Lab Integration

To make this phase perfectly align with the high standards of Phases 1-3, I recommend three minor adjustments:

#### 1. Scope Down the Bedrock IAM Permission
Your README showed `"Resource": "*"` for `bedrock:InvokeModel`. As we established in Phase 3, this is a security anti-pattern. Update your IAM policy to target the specific model:
```json
{
  "Sid": "InvokeBedrock",
  "Effect": "Allow",
  "Action": ["bedrock:InvokeModel"],
  "Resource": "arn:aws:bedrock:REGION::foundation-model/anthropic.claude-3-haiku-20240307-v1:0"
}
```

#### 2. Address the `reportlab` Dependency Explicitly
Since `reportlab` contains C-extensions, you cannot just upload the `.py` file. You have two options for your lab:
*   **Option A (Lambda Layer - Recommended)**: Use a pre-built public Lambda Layer for ReportLab, or build your own using a Docker container that matches the Amazon Linux runtime (`public.ecr.aws/lambda/python:3.12`), run `pip install reportlab -t /python`, and zip it.
*   **Option B (Local Packaging)**: If you are on Linux/macOS, you can run `pip install --platform manylinux2014_x86_64 --target=./package --implementation cp --python-version 3.12 --only-binary=:all: --upgrade reportlab`, zip the `./package` folder along with your `executive_dashboard_agent.py`, and upload that zip to Lambda.

#### 3. Acknowledge the Scan vs. Query Trade-off
The code already has a great comment about this: *"A later production revision should use reporting-oriented indexes and Query operations."* 
In your documentation, explicitly state that for this lab, the `MAX_ITEMS_PER_TABLE` cap makes the `Scan` operation safe and cost-predictable, but in a real enterprise environment, you would create a Global Secondary Index (GSI) on the `created_at` or `event_epoch` fields to use efficient `Query` operations instead.
